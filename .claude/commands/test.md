以测试驱动开发（TDD）方式推进：先写失败测试，再写实现，最后重构。修复 Bug 时使用"先复现再修复"模式。

---

## 新功能开发（TDD 流程）

1. **RED — 写失败测试** — 根据验收标准编写描述期望行为的测试，运行并确认测试**失败**（失败原因应是"功能不存在"，而非测试代码本身有误）
2. **GREEN — 最小实现** — 只写刚好能让测试通过的代码，不过度设计
3. **REFACTOR — 重构** — 在测试保持绿色的前提下改善代码结构、消除重复、提升可读性

每完成一个 RED → GREEN → REFACTOR 循环，运行完整测试套件确认无回归，再进入下一个功能点。

---

## Bug 修复（先复现再修复模式）

1. **写复现测试** — 编写一个能稳定触发该 Bug 的测试，运行并确认**测试失败**（失败即证明 Bug 已复现）
2. **确认复现** — 确保失败原因与 Bug 描述一致，不是测试写错了
3. **实现修复** — 修改最小范围的代码来修复 Bug
4. **确认修复** — 运行复现测试，确认**测试通过**
5. **回归验证** — 运行完整测试套件，确认未引入新问题

---

## 通用注意事项

- 测试命名要表达"什么场景下期望什么结果"，而非"测试某方法"
- 每个测试只验证一个行为，保持测试的原子性
- 不要为了让测试通过而修改测试断言（除非断言本身写错了）
- 若某个功能难以测试，优先考虑是否需要调整设计，而非放弃测试
