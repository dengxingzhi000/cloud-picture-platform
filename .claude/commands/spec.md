在写任何代码之前，先通过提问与用户对齐需求，再生成结构化规格说明书（SPEC.md），用户确认后方可进入实现阶段。

**第一步：澄清需求**

向用户提问以下几个方面（每次不超过 3 个问题，避免一次性轰炸）：

1. **目标与用户** — 要解决什么问题？目标用户是谁？
2. **核心功能** — 必须实现哪些功能？每个功能的验收标准是什么？
3. **技术约束** — 技术栈偏好？有哪些不可违反的约束（如必须兼容已有服务、禁用某些框架）？
4. **边界规则** — 哪些操作必须自动执行？哪些操作需要先询问？哪些操作绝对禁止？

**第二步：生成 SPEC.md**

基于用户的回答，在项目根目录生成 `SPEC.md`，必须覆盖以下六个核心部分：

```markdown
# 项目规格说明书

## 1. 目标
[用一段话描述要构建什么、为谁构建、解决什么问题]

## 2. 指令与工作流
[AI 在此项目中可以使用哪些命令？默认工作流是什么？]

## 3. 项目结构
[目录布局、模块划分、关键文件说明]

## 4. 代码风格
[命名规范、格式化工具、注释要求、禁止的写法]

## 5. 测试策略
[单元测试 / 集成测试 / E2E 测试的划分；覆盖率要求；测试命名约定]

## 6. 边界规则
- **必须执行**：[无需询问即可自动执行的操作]
- **先问后做**：[执行前必须获得用户确认的操作]
- **永远禁止**：[绝对不能做的操作]
```

**第三步：等待确认**

将 SPEC.md 呈现给用户，等待明确确认（"可以"、"没问题"、"开始吧"等）后，才可进入计划或实现阶段。不要在用户确认前开始写任何业务代码。
